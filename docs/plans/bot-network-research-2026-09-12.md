# Bot friendships and reviewed knowledge sharing

Read-only primary-source review, 12 September 2026. No installations, registrations, credentials, posts, model calls, or runtime tests. Published documentation establishes advertised contracts; it does not prove deployed behavior or security.

## What is available

- **AgentGram:** a public social application with Next.js/Supabase implementation, agent registration, posts, comments, profiles and follows. Its [repository](https://github.com/agentgram/agentgram) lists federation as future work. The [actual follow handler](https://github.com/agentgram/agentgram/blob/d811f86fcb5fa8590484dcecc51bc26f3e859763/packages/db/src/follow.ts) toggles following immediately: it is neither a mutual friend request nor an idempotent operation; retry can unfollow. The [quickstart](https://www.agentgram.co/docs/quickstart) documents bearer-authenticated posting and explicitly distinguishes private starter memories from public content. It recommends `memoryConsent:false` and acknowledges no starter-memory-specific training disclosure there. Useful feed/profile patterns; do not copy automatic memory seeding or assume federation exists.

- **OASIS/CAMEL:** [OASIS](https://github.com/camel-ai/oasis) implements simulated social environments, recommendations and agent actions; its [paper](https://arxiv.org/abs/2411.11581v5) studies information spread, polarization and herd effects. “One million” concerns simulated agents, not verified active customers or throughput for a deployed social service. [CAMEL-AI](https://www.camel-ai.org/) is the broader multi-agent research/framework community. Use OASIS later for isolated synthetic evaluation of spam, feedback loops and approval policies; it supplies no production friendship, owner-consent or cross-network interoperability guarantee. Its example requires model access; this review executed none.

- **AI Social:** the [repository](https://github.com/Kevinchamplin/ai-social) contains API documentation, OpenAPI and examples, not a server implementation. It advertises an autonomous feed, approval before agent activation, and post/reply endpoints. Activation approval is not per-post human approval. The advertised public feed returned a web-fetch 502 during this review; that is an observation, not proof the service is permanently unavailable. Treat it as a possible external adapter, not a backend to adopt or verified deployed capacity.

- **hi.new:** [the service](https://hi.new/) and [source](https://github.com/elie222/hi-new) describe invite-based, store-and-forward bot messaging rather than a public feed. [Routes](https://github.com/elie222/hi-new/blob/9fbffdc8f041aebceccaf835653f59970f80e347/apps/api/src/routes/invites.ts) create single-use invitations, mutual grants, key-change indications and bilateral revocation. [API documentation](https://hi.new/api.md) defines DM idempotency keys, acknowledgement and payload expiry. Encryption depends on publishing an age key; plaintext exists. **Retention conflict:** the homepage says plaintext transcript retention requires explicit opt-in, while live API documentation and the [pinned schema](https://github.com/elie222/hi-new/blob/9fbffdc8f041aebceccaf835653f59970f80e347/apps/api/src/db/schema.ts) describe/default to 90 days. Resolve before sending private knowledge. The built-in welcome bot is documented as canned text, not evidence of autonomous collaboration.

## Proposed first slice

Build one explicit **share-with-a-known-bot** journey: a human reviews the peer identity and purpose, approves an invitation/acceptance, then reviews one bot-generated knowledge excerpt before sending. Scope the excerpt to selected source material, with citations; exclude blanket memory access. Show draft → approved → submitting → accepted/unknown/failed receipts. Keep public feed publishing as a later, separately approved destination. Reuse Muster's existing approval machinery after checking its social transport boundary; do not add a second general agent runtime.

Acceptance should use two isolated owners: rejection sends nothing; only both approvals establish friendship; revoked/stale peers cannot send; changed content requires renewed approval; double taps and restart cannot duplicate an accepted message; uncertain delivery reconciles without automatic replay.

## Approval and disclosure rules

Default private. Explicitly show destination, audience, exact text/attachments, source provenance, retention and account before approval. Label the author as an AI bot acting for a human; distinguish observed facts, generated claims and simulation. Never export credentials, private transcripts or whole memory by default. Permission to receive does not authorize execution, replies, knowledge ingestion or public reposting. Treat incoming content as untrusted data; retain provenance and require approval before adopting it as knowledge. Bind approval to immutable content, target and session identity; cancel stale approval on edits/account changes. Keep block/revoke controls, bounded rates/costs and a human-readable delivery history. External adapters must fail closed when audience, retention or result semantics are unknown.

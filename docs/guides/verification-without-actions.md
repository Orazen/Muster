# Private-repository CI alternative — 12 September 2026

**Recommendation: run verification directly on existing owned machines, outside GitHub Actions, and retain evidence locally.** This avoids new hosted-CI charges and the Actions scheduler while keeping the repository private. It consumes existing machine time/storage; it does not turn blocked GitHub checks green.

GitHub currently documents self-hosted runner usage as free, with machine maintenance borne by the owner. Its pricing announcement explicitly **postpones** the proposed March 2026 self-hosted charge. However, runners still execute jobs dispatched by GitHub Actions. Neither inspected document establishes that this account's billing restriction permits self-hosted jobs to start. Thus an owned runner is a possible later option, **not a verified billing bypass**; registration and an authorized bounded trial would be needed. Artifact/cache storage also has separate billing rules. [Runner documentation](https://docs.github.com/en/actions/concepts/runners/self-hosted-runners), [billing documentation](https://docs.github.com/en/billing/concepts/product-billing/github-actions), [updated pricing announcement](https://github.blog/changelog/2025-12-16-coming-soon-simpler-pricing-and-a-better-experience-for-github-actions/).

The retained Loop49 annotation receipt records four jobs rejected before any step executed and one dependent job skipped. I reused that historical evidence rather than retrying unchanged failures or asserting a freshly measured account state: [tracked audit](../plans/astra-glm-audit-2026-09-12.md) (local raw receipt: `.omb-scratch/verification/loop49-watch/actions-current.json`).

Reviewed four workflow files plus relevant package/release/deployment helpers. `ci.yml` uses hosted Ubuntu for lint, types, tests and build. `release.yml` additionally gates macOS arm64/Intel, Windows and Linux packages, runtime smoke, signatures where configured, updater feeds and staged publishing. `package-win.yml` uses hosted Windows and Actions artifact upload. `autodeploy.yml` runs independently of CI success, pushes a `.deploy-trigger` commit and invokes a Dokploy webhook. These are distinct verification, artifact and deployment responsibilities.

The next bounded implementation candidate is **`scripts/verify-local-ci.mjs` plus focused runner tests**, optionally exposed as `pnpm verify:local`. Suggested invocation: `node scripts/verify-local-ci.mjs --sha <40-hex-main-SHA> --out <owned-evidence-directory>`.

1. Require the requested source SHA and a clean owned checkout; pin the lockfile/source hashes and Node 24/pnpm 10.33.0. Use owned HOME/data/temp paths and an explicit environment allowlist; no inherited provider credentials or production URLs.
2. Install with `pnpm install --frozen-lockfile`, then run existing gates sequentially: `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm check:electron`. `pnpm test` already includes root Vitest, broker tests, updater tests and the standalone packaged-server build/smoke. Do not duplicate them or describe host-Node smoke as packaged Electron validation.
3. Record each exact command, exit, elapsed time and log hash; stop on failure. Record source hashes again, process/port cleanup and an explicit overall outcome. Cancellation or changed source must never yield success. Keep artifacts/receipts on owned disk; no Actions uploads, statuses, tags, releases or deployment side effects.
4. Verify runner orchestration with failing-command, cancellation, source-change and owned-cleanup cases, then run the actual gate once. Add task-relevant existing browser tests separately when required. Do not use `scripts/e2e-server.mjs` as a generic offline gate: it runs actual providers and optionally provisions boxes.

Manual release acceptance can reuse `release-native-smoke.mjs`, package validators, feed/hash checks and release policy on the exact artifacts. A Mac result does not validate Windows/Linux or notarization. Keep unavailable platform gates explicit and the candidate unpublished; retain existing signing and publishing policy.

Dokploy's GitHub integration/webhooks can deploy independently of Actions, and watch paths can restrict triggers. This is an architectural alternative, not verification of the live deployment configuration. After separately authorized release/deploy work, check production using **GET only**. Do not run `deploy-prod.sh` as CI: it pulls, installs and stops/restarts containers. Preserve current deployment policy until a separate reviewed change binds deployment to the verified source. [Dokploy GitHub integration](https://docs.dokploy.com/docs/core/github), [auto-deploy methods](https://docs.dokploy.com/docs/core/auto-deploy), [watch paths](https://docs.dokploy.com/docs/core/watch-paths).

No runner, daemon, billing, secret, repository-visibility, release or production mutation was performed in this audit.
